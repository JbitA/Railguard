# Native runtime performance evaluation

This document separates measurements that were actually executed from deployment measurements that require Jetson hardware.

## Host CPU microbenchmark

Run on 2026-08-20 in the repository validation environment:

- CPU: Intel Xeon Platinum 8573C (5 vCPUs exposed)
- architecture: x86_64
- compiler: GCC 14.2, `-O3`-class Release build via CMake
- Python: 3.13.5
- iterations: 200,000 packet decodes per run
- repeats: 7; table values are medians
- DSP window: 512 samples at 2 kHz, RMS/peak/kurtosis plus four Goertzel diagnostic bins

Command:

```bash
make benchmark
```

Measured result (`benchmarks/results/latest.json`):

<!-- BENCHMARK_TABLE_START -->
| Operation | Python reference | C++20 native | Improvement |
|---|---:|---:|---:|
| Legacy CRC packet decode | 1173 ns | 455 ns | **2.58x** |
| 94-byte production packet decode | 1948 ns | 915 ns | **2.13x** |
| 94-byte production throughput | 0.513 Mpacket/s | 1.093 Mpacket/s | **2.13x** |
| Production decode + semantic/timestamp validation | 4672 ns | 916 ns | **5.10x** |
| Validated production throughput | 0.214 Mpacket/s | 1.092 Mpacket/s | **5.10x** |
| 512-sample DSP window | 119.90 us | 5.98 us | **20.06x** |
<!-- BENCHMARK_TABLE_END -->

The packet benchmark exercises byte-identical framing in Python and C++. The DSP benchmark uses matched mathematical operations in both implementations, but it is a microbenchmark rather than a complete end-to-end pipeline. It should be interpreted as evidence that high-rate feature extraction belongs in native code, not as a claim about overall application speedup.

At the intended 10 Hz feature publication rate, a 5.98 us native DSP window represents far below 1% of one CPU core. More importantly, native code keeps the high-rate acquisition path outside the Python interpreter and makes bounded buffering/backpressure explicit.

## Protocol correctness

The C++ tests include a byte-for-byte test vector generated by the Python protocol implementation. CRC corruption and stream resynchronization are also tested:

```bash
ctest --test-dir build/edge-cpp --output-on-failure
```

## Firmware host validation

The portable firmware modules are compiled as C17 with `-Wall -Wextra -Werror`. The host test validates:

- NMEA RMC UTC conversion;
- binary packet size/layout;
- CRC32 compatibility.

```bash
make firmware-host-test
```

The STM32 HAL/DMA source itself requires STM32Cube-generated HAL headers and a cross compiler, so host CI intentionally validates only the portable modules. Hardware validation still needs a real STM32H743 + IIS3DWB board, logic-analyzer traces and sustained FIFO-overrun testing.

## TensorRT evaluation plan

The current validation environment has no NVIDIA CUDA compiler or TensorRT runtime, so no GPU latency/FPS number is reported. The repository provides reproducible commands instead of invented figures:

```bash
python ml/export_onnx.py models/fusion_transformer.pt
./deploy/tensorrt/build_engine.sh models/fusion_transformer.onnx models/fusion_transformer_fp16.engine
./deploy/tensorrt/benchmark_engine.sh models/fusion_transformer_fp16.engine
```

On the Jetson, record at least:

- JetPack, CUDA and TensorRT versions;
- power mode and clocks;
- sequence length and image size;
- FP32 / FP16 / INT8 precision;
- p50/p95 inference latency;
- throughput;
- GPU/CPU memory;
- end-to-end sensor-to-prediction latency;
- model accuracy before/after quantization.

Accuracy should be compared on the same held-out Rail-VIVID physical runs so a faster engine is accepted only when its forecast/anomaly degradation is understood.
